1. The problem
Insurance claims and service cases go through many hands before a decision is made. Today, most of this work is manual, which makes it slow, error-prone and hard to track. Claims and case teams face five everyday problems:
Manual intake — claim details are typed in by hand from emails, forms and phone calls.
Document-heavy work — adjusters read every invoice, report and photo to find the facts they need.
Scattered information — policy, customer and document data sit in different systems.
Long approval chains — cases wait in queues because nobody knows who should act next.
Poor visibility — customers and managers cannot easily see where a case is or why it is delayed.
Together these increase cycle time and make accurate, compliant servicing difficult.
Your challenge
Build a multi-agent AI system that captures a claim, reads and classifies its documents, summarises the evidence, assigns the right people, manages approvals and shows real-time status — with a secure, replayable audit trail of everything that happened.
2. What you will build
A LangGraph supervisor coordinates five LangChain specialist agents. The agents never talk to each other directly. They read and write the case only through four MCP servers, so every hand-off is stored in the case record and the audit log. A person always makes the final decision.
2.1 The happy path for a new claim
Claim submitted
→
Intake agent
→
Document agent
→
Summary agent
→
Routing agent
→
SLA & comms agent
→
Human approver
The supervisor decides the order at run time. If documents are missing, the graph pauses and waits for them. If confidence is low or a step keeps failing, the case goes to manual review.
The golden rule: agents prepare, people decide
No agent and no MCP tool can approve, reject or settle a claim. The graph pauses with interrupt() and only a signed-in approver can resume it with a decision.
2.2 Five design rules to follow
Talk through MCP only. Agents reach data and actions only through MCP tools, resources and prompts.
Least privilege. Each agent gets only the tools it needs (see section 4.1).
Humans decide. There is no approve tool. Approvals happen at a LangGraph interrupt.
Document text is data, not orders. Any instruction found inside a document is flagged and ignored.
Everything is recorded. Every MCP write and human decision goes into an append-only audit log.

4.3 The LangGraph orchestration
Concept
How you use it
State
ClaimState holds: case ID, messages, case status, next step, agent hops, stage results, human decision, errors and token usage.
Nodes
supervisor, the five specialists, human_review, await_documents, finalize and manual_review.
Routing
The supervisor returns Command(goto=...). A guard function allows only moves that fit the case status (for example, no routing before a summary exists). Repeated failures go to manual_review.
Parallel work
Send fans out one task per document; results are joined before validation.
Human-in-the-loop
interrupt() pauses the graph at human_review and await_documents. Streamlit resumes it with Command(resume=...) carrying the decision, rationale and approver.
Persistence
PostgresSaver checkpointer with thread ID = case ID, so a case can wait days and survive restarts. Checkpoint history allows replay for audits and debugging.
Streaming
stream_mode “updates” and “messages” show live agent progress in Streamlit.
Resilience
RetryPolicy on nodes, model fallback middleware and a recursion limit stop transient errors and endless loops.

Task 1 — Build the MCP servers (~45 min)
Objective: Expose claims capabilities through one standard protocol.
Build case-mcp and policy-mcp with FastMCP: the lookup and registration tools, the case://{case_id} and policy://{policy_number} resources, and the case_summary prompt.
Build documents-mcp: extract_text with Docling (OCR on), and classify_document and extract_fields with LLM structured output. Return the OCR confidence and flag any text that tries to instruct the system.
Build workflow-mcp: workload, assignment, approval request, SLA scheduling, notifications through Mailpit and document requests. Do not add any tool that approves.
Test every server in MCP Inspector over stdio, then start them over Streamable HTTP with Docker Compose.
You are done when...
✓  All four servers start with Docker Compose.
✓  Every tool, resource and prompt works in MCP Inspector.
✓  No tool can approve, reject or settle a claim.
Task 2 — Build the specialist agents with LangChain (~40 min)
Objective: Create five agents that each do one job well.
Load tools from the four servers with the LangChain MCP adapter, and give each specialist only the tools listed in section 4.1.
Create each specialist with create_agent: its own system prompt, a small model, and middleware (PIIMiddleware for emails and ID numbers, ToolCallLimitMiddleware, ToolRetryMiddleware).
Load the case_summary and claimant_letter prompts from MCP instead of hard-coding them.
Test each specialist on a clean pack, a poor scan, a missing document, a duplicate and the prompt-injection pack.
You are done when...
✓  Each agent works on its own against the test packs.
✓  Each agent can see only its permitted tools.
✓  PII is redacted before it reaches the model.
Task 3 — Orchestrate the agents with LangGraph (~50 min)
Objective: Create one supervised, durable process from intake to decision.
Define ClaimState and the nodes from section 4.3.
Write the supervisor: structured output Route(next, reason), a guard function for allowed moves, and a path to manual_review for low confidence or repeated failure.
Fan out document processing with Send, then join the results for validation.
Add interrupt() for approval and for missing documents, with a PostgresSaver checkpointer keyed by case ID.
Run claims end to end from a script: approve, reject, request more information and the low-confidence path. Replay one case from its checkpoint history.
You are done when...
✓  A clean claim runs from intake to the approval pause.
✓  A paused case survives a restart and resumes correctly.
✓  Out-of-order moves are blocked by the guard function.
Task 4 — Build the Streamlit claims workspace (~35 min)
Objective: Give adjusters and approvers one place to work.
Add sign-in with st.login against Keycloak, and read the adjuster, approver and supervisor roles from the token.
Build the pages: submit a claim with documents, the case queue, and a case workspace showing summary, documents, extracted fields, timeline and live agent progress from graph streaming.
Build the approvals page: the approver reads the summary and risks, then approves, rejects or asks for more information with a rationale. After checking the approver’s role and limit, the app resumes the graph with Command(resume=...).
Add an “Ask the supervisor” chat that answers questions about a case from MCP resources, with streamed replies.
Task 5 — Govern, observe and audit (~25 min)
Objective: Make every agent action visible, safe and traceable.
Trace every run in Phoenix with OpenInference: agent hops, MCP tool calls, tokens and latency per node.
Write every MCP write and human decision to the append-only audit table (actor, time, before and after), linked to the checkpoint history.
Check PII redaction in traces and messages, confirm the injection pack is flagged and ignored, and trigger an SLA breach to see the escalation email in Mailpit.
You are done when...
✓  Every run is visible as a trace.
✓  The audit log shows who did what and when.
✓  No PII leaks; injection is blocked; the SLA escalation email arrives.
Task 6 — Evaluate the agents (~45 min)
Objective: Prove quality with numbers before any release (see section 8).
Load the golden dataset (inputs, expected outcomes, trajectories, labelled fields) into Phoenix.
Run the evaluation harness: deterministic metrics, agentevals trajectory matching and openevals judges.
Review the results in a Streamlit evaluation dashboard and Phoenix experiments. Change one prompt or model tier, rerun and compare.
Add the release gate: CI fails when any metric misses its threshold.

Tips for using LLM judges
Use a judge model that is stronger than your agent models, ideally from a different model family. Have a person spot-check about 10% of judge scores. Thresholds are lab starting points, not production values.
